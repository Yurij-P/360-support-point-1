# AGENTS.md — інструкція для AI-агентів у TPS360

Цей файл задає обов'язковий порядок роботи для AI-агентів у репозиторії
`Yurij-P/360-support-point-1`.

## 1. Джерела істини та пріоритет

1. `MASTER_PROJECT.md` — головне джерело доменних вимог і статусу реалізації.
2. `SKILL.md` — обов'язковий процес виконання задач.
3. Профільні стандарти/ADR у `docs/`.
4. Код і тести — лише як доказ поточної реалізації, а не затвердженої поведінки.

Якщо `MASTER_PROJECT.md` відсутній, зупиніть імплементацію та повідомте про блокер.

## 2. Що робити перед будь-якою зміною

1. Перевірити гілку, `HEAD` і `git status`.
2. Прочитати `MASTER_PROJECT.md` і `SKILL.md`.
3. Знайти релевантні документи/ADR/тести.
4. Зафіксувати мапу:
   `документ → погоджена вимога → backend → frontend → розбіжність → зміна`.
5. Кожну зміну класифікувати як:
   - погоджена вимога;
   - технічний наслідок погодженої вимоги;
   - нова пропозиція (потребує погодження користувача до реалізації).

## 3. Непорушні доменні інваріанти TPS360

- Платформа універсальна для різних громад; назви конкретних громад не хардкодити.
- Кожна симуляція прив'язана до вибраної громади й версіонованого контексту.
- Реальні дані громади/карти відокремлювати від стану сценарію/симуляції.
- Фасилітатор і гравці мають ізольовані повноваження та серверну авторизацію.
- Не вигадувати ролі, ієрархію, ресурси, права чи задачі без затверджених вимог.
- Не називати прототип/чернетку валідованим продуктом.

## 4. Правила внесення змін

- Працювати малими вертикальними зрізами: документування рішення → домен →
  сервіс/API → тести → frontend.
- Не спрощувати доменну логіку заради демо-інтерфейсу.
- Не змішувати фасилітаторський і рольовий інтерфейси.
- Не покладатися на приховування в UI там, де потрібні серверні обмеження доступу.

## 5. Мінімальна перевірка перед передачею

Запустити:

```bash
pytest
ruff check .
mypy
git diff --check
git status --short --branch
```

Якщо щось не запускається — явно вказати причину, не підміняти результат оцінкою.

## 6. Коли зупинятись і ставити питання

Зупиніться й запитайте користувача, якщо:

- відсутнє затверджене продуктове рішення;
- конфліктують погоджені документи;
- треба самостійно вибрати ролі/ієрархію/права/ресурси;
- зміна зачіпає несуміжні або незапитані користувацькі правки.
