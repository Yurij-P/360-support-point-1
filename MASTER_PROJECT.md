# Повний статут та інструкція проєкту TPS360

Документ описує стан проєкту, правила реалізації, обмеження, доменні вимоги
та обов'язковий порядок роботи для розробника й AI-асистента.

## 1. Загальні положення

- **Назва проєкту:** TPS360 (360 Support Point).
- **Призначення:** веб-платформа підтримки рішень, навчання та оцінки готовності
  громад до кризових ситуацій через рольове симуляційне моделювання.
- **Поточний етап:** технічний прототип v0.2.8 — підготовка до пілотування (Pilot Preparation).
  Основні доменні модулі, FastAPI-сервер і тести реалізовані; додано шар персистенції на
  SQLAlchemy (ADR-0012), API Каталогу ролей і Конструктора кризи. Лишаються
  production-конфігурація PostgreSQL, Auth/RBAC та повноцінний frontend.

## 2. Ключові принципи

1. Документи мають найвищий пріоритет над кодом.
2. Новий код не повинен ламати існуючий доменний шар, геопросторову модель та
   регламенти симуляції.
3. Перед будь-якими змінами необхідно перевірити `SKILL.md` та `MASTER_PROJECT.md`.
4. Заборонено видаляти або спотворювати доменну логіку ради швидкого visual demo.
5. Будь-які зміни описуються у робочому журналі та додаються тестами.

## 3. Доменні шари та модулі проєкту

Код проєкту знаходиться в `src/tps360/`:

- `core/` — базові типи, виключення та спільні утиліти;
- `community/` — доменні моделі громади, паспорта, ресурсів та профілю готовності;
- `geospatial/` — картографічний шар, геопросторові координати, межі громади;
- `threat/` — онтологія загроз, класифікація криз та ланцюжки впливу;
- `simulation/` — рушій симуляції, раунди, такт часу, рішення ролей, доручення;
- `api/` — FastAPI ендпоінти для взаємодії з веб-інтерфейсом.

## 4. Джерельні вимоги та стандарти

Код та архітектура спираються на документи в репозиторії:

- `docs/architecture/` — технічна архітектура та ADR;
- `docs/standards/` — методичні стандарти готовності та симуляцій;
- `docs/ux-ui/` — концепція та дорожня карта веб-інтерфейсу;
- `CHANGELOG.md` — журнал релізів та змін.

## 5. Рольова модель та поділ доступу

У симуляції беруть участь:

- **Фасилітатор (Модератор гри):** створює сесію, модерує перебіг гри, надсилає вводні (інжекти), перевіряє рішення гравців та запуск раундів.
- **Системний Адміністратор:** керує налаштуваннями баз знань, моделями ШІ та інтеграційними модулями.
- **Ролі-учасники** беруться з **каталогу КАТОТТГ-рольової моделі** (`role_catalog_service`, 7 категорій / 23 позиції, стандарт `TPS360-ROLE-UX-001`), а командна модель визначена в `ADR-0015` (Incident Command System: Голова громади — командир штабу). Операційні ролі рушія симуляції узгоджені з каталогом:
  - Представник ДСНС (`emerg-dsns`);
  - Представник екстреної медичної допомоги (`emerg-ems`);
  - Представник поліції (`emerg-police`);
  - Комунальне підприємство (`communal-utility`);
  - Санітарний інспектор (`chief_sanitary_inspector`) — погоджена сценарна роль поза каталогом (`TPS360-ROLE-UX-001` §5.2).
- **Ресурси ролей** визначаються стандартом `TPS360-RES-001` (відкритий перелік, персонал як першокласний ресурс, реалістичні активи, виведення кількостей з паспорту/КАТОТТГ). Поточні сіди в коді — тимчасові заглушки.

Кожен гравець бачить лише свою рольову інформацію, власні завдання та доручення через ізольовані токени автентифікації (`X-Participant-Token`).

## 6. Геопросторова модель та межі OpenStreetMap

- Географічні межі симуляційної події суворо обмежені полігоном громади з **OpenStreetMap (`openstreetmap.org`)**.
- Об'єкти інфраструктури прив'язані до офіційних тегів OSM (понад 40+ категорій: АПК, ГЕС/АЕС, військовий компонент, транспорт, трубопроводи, річки, ліси).
- Динаміка загроз розраховується з урахуванням реального рельєфу та картографії громади.

## 7. Модель дилатації часу та AI Crisis Copilot

- Дилатація часу задається коефіцієнтами швидкісного масштабування (1:30, 1:60, 1:90).
- **AI Crisis Copilot** моделює розвиток подій під модерацією Фасилітатора.
- ШІ заземлений на об'єктивні факти реальних воєнних подій (`EmpiricalCrisisIncidentFact`), протоколи повторних ударів (Double-tap) та радіуси розльоту БК, виключаючи штучне видумування подій.

## 8. Фактичний стан реалізації

### Наявне

- доменні модулі Core, Community Profile, Geospatial, Threat і Simulation;
- версіонований контекст симуляції для конкретної громади;
- Simulation State, timeline, scheduler, decision та impact engine;
- серверна автентифікація й авторизація фасилітатора/гравців (токени `X-Facilitator-Token`, `X-Participant-Token`);
- доменна модель спроможностей та сумісності ролей (`participant_capability`);
- детермінований рушій виконання задач і резервування ресурсів за раундами (`TaskRoundExecutionEngine`);
- система доручений та контрактів рольових завдань (`TaskDirective`, `RoundExecutionService`);
- математична доменна модель дилатації часу (`SimulationRoundClock`, співвідношення 1:30, 1:60, 1:90 для пожеж, епідемій холери, падіжу худоби, ізоляції);
- транспорт синхронізації стану в реальному часі Server-Sent Events (SSE) та шина подій (`SessionEventBroadcaster`, `/events/session/{id}/stream`);
- відкрита онтологія криз та автономний **AI Crisis Copilot** (`AICrisisCopilotService`), заземлений на реальні факти воєнних подій (`EmpiricalCrisisIncidentFact`), протоколи повторних ударів (Double-tap) та радіуси розльоту БК під модерацією Фасилітатора;
- суворе геопросторове обмеження подій ШІ межами OpenStreetMap (OSM BoundingBox / Relation) громади;
- вичерпна онтологія 40+ категорій об'єктів критичної інфраструктури, АПК, видобутку та військового компонента (`CriticalInfrastructureCategory`, `OSMTagMapping`);
- агрегована читацька модель Паспорта громади (`CommunityPassportReadModel`, `InfrastructureItemReadModel`) та REST API Каталогу громад (`GET /communities/catalog`, `GET /communities/{id}/passport`);
- сервіс каталогу сценаріїв та картографічний рушій евалуації сумісності за рельєфом (`ScenarioCatalogService`, `SpatialTopographyFeature`, `ScenarioCompatibilityEvaluator`), що перевіряє можливість виникнення загрози за картою громади (гірський рельєф/Верховина vs рівнинний степ/Широке, близькості АЕС) з універсальною сумісністю ракетно-дронових загроз;
- передстартовий агрегований контекстний зріз симуляції (`SimulationContextSnapshotReadModel`) та REST API Сценаріїв (`/scenarios/catalog`, `/scenarios/compatibility-check`, `/simulations/{id}/context-snapshot`);
- сервіс кімнати очікування Лобі та реєстрації гравців (`SessionLobbyService`, `LobbyParticipantStatus`, `LobbyRoomStatus`) з конфігуратором місткості (Демо 1-50, Продакшн 5-20), призначеням ролей та суворим бар'єром старту сесії (Pre-start Readiness Guard);
- сервіс рольових кабінетів, відкритих конструкторів карточок LEGO, 100% списання ресурсів та перерозподілу ресурсів ОМС (`RoleDashboardService`, `LegoDecisionCard`, `ResourceTransferDirective`, `RoleWorkspaceReadModel`);
- головна пульт-консоль Фасилітатора (`FacilitatorConsoleService`, `FacilitatorConsoleReadModel`, `CrisisLifecycleProjectionVariant`), рушій бачення на 1 раунд уперед з 5 проєкціями розвитку НС, модерація інжектів ШІ, розрахунок об'єктивних ресурсних потреб ШІ та динамічне оцінювання ШІ тривалості гри (`COMPLETED_SUCCESS`);
- рушій психологічного навантаження та фрикцій у Кабінеті гравця (`PsychologicalFrictionInject`): сирени повітряної тривоги (аудіо/візуальний сигнал), термінові телефонні дзвінки, паніка у соцмережах/Telegram-каналах, протести мешканців під міськрадою, побутові форс-мажори (загублені ключі);
- сервіс After-Action Review (AAR) та аналітичної телеметрії (`AARTelemetryService`);
- рушій двостороннього навчання ШІ та банку пам'яті досвіду гравця (`ParticipantExperienceRecord`): ШІ аналізує тактичний стиль гравця та у наступних іграх **НІКОЛИ не повторює однаковий сценарій розвитку подій**, а підкидає нові життєві обставини (зміна вітру, пошкодження доріг, дефіцит ПММ);
- підсумковий звіт дебрифінгу AAR (`AfterActionReviewReport`), часова телеметрія змін спроможностей ролей та когнітивного стресу за раундами (`RoundTelemetrySnapshot`);
- типізований Web API Клієнт (`src/frontend/api_client.ts`) та картографічний модуль OpenStreetMap GIS (`src/frontend/osm_map_viewer.ts`);
- REST API для AAR дебрифінгу (`/aar-report`), часової телеметрії (`/telemetry`), пам'яті досвіду учасника (`/experience-record`), Консолі Фасилітатора (`/facilitator-console`, `/future-projections`, `/injects/approve-ai-proposal`, `/injects/psychological-friction`, `/rounds/advance`), кабінету ролі (`/role-workspace`), LEGO-карткам (`/lego-decisions`), розрахунку ресурсів ШІ (`/ai-resource-estimate`), переказам ресурсів ОМС (`/resource-transfers`), лобі, сесіям, симуляціям, дорученням (`/directives`), подіям (`/events`), каталогу (`/communities/catalog`), сценаріям (`/scenarios`) та профілям готовності;
- FastAPI сервер;
- REST API Каталогу ролей (`/roles/catalog`, `/roles/catalog/{role_id}`, `/sessions/{id}/roles/me`);
- REST API Конструктора кризи фасилітатора (`/sessions/{id}/crisis`, `/crisis/define`, `/crisis/add-condition`);
- шар персистенції на SQLAlchemy (`tps360.db`, ADR-0012) та дублювання ключових маршрутів під префіксом `/api/v1` для веб-клієнта;
- ідентифікація громад за офіційними кодами КАТОТТГ (ADR-0014): громада обирається з каталогу, а не зашивається у код;
- **enforcement командної ієрархії ICS** (ADR-0015): авторизація видачі директив за ланцюгом issuer→assignee (`command_hierarchy`, `POST /directives` → 403 на нелегальне ребро) та контракт **ескалацій** знизу вгору (`EscalationService`, `POST/GET /sessions/{id}/escalations`);
- 610 автоматизованих тестів домену, API та frontend-інтеграції з 100% проходженням.

### Частково або відсутнє

- повна рольова модель (перелік/повноваження) ще потребує погодження (§11); командну ієрархію ICS та авторизацію директив/ескалацій уже реалізовано (ADR-0015);
- повний AAR/дебрифінг у web-інтерфейсі;
- production-конфігурація персистенції (PostgreSQL) та Auth/RBAC.

## 9. Заборонені підміни

- Не зашивати конкретну громаду або сценарій у frontend як універсальну модель.
- Не створювати ролі, ієрархію, ресурси або завдання без специфікації.
- Не змішувати інтерфейс фасилітатора з інтерфейсом гравця.
- Не показувати гравцеві серверно заборонені рольові дані, покладаючись лише на приховування елементів у браузері.
- Не називати прототип валідованим продуктом або методикою.
- Не змінювати архітектуру лише для відповідності наявному демонстраційному UI.

## 10. Обов'язковий порядок роботи

Перед зміною:

1. Перевірити репозиторій, гілку, HEAD і `git status`.
2. Повністю прочитати `SKILL.md` і цей файл.
3. Знайти релевантні стандарти, ADR, доменні правила та тести.
4. Скласти відповідність: `документ → погоджена вимога → backend → frontend → розбіжність`.
5. Позначити кожен новий елемент як:
   - підтверджена вимога;
   - технічний наслідок підтвердженої вимоги;
   - нова пропозиція, що потребує погодження.
6. Реалізовувати лише підтверджені вимоги й необхідні технічні наслідки.
7. Після зміни запустити тести, Ruff, MyPy і `git diff --check`.
8. Оновити документацію та робочий журнал, якщо змінився фактичний стан.

## 11а. Відкриті рішення

До окремого погодження не визначати самостійно:

- повний перелік і назви ролей (Трек B3 / D4);
- підпорядкування та право ставити завдання (D5);
- ресурси й об'єкти управління кожної ролі;
- допустимість дублювання ролей;
- join code format та participant reconnect model (D3);
- структура конструктора кризи (Трек B4);
- geospatial provider для production (D6);
- evaluation rubric та ownership (D7);
- AAR/Debriefing формат та participant input (D8);
- report template, approval, export formats (D9);
- archive retention та access rules (D10);
- community passport fields та data freshness (D11);
- модель умовних навчальних об'єктів поверх реальної карти.

## 12. Критерій релізного зрізу v0.2.8

Релізний зріз повністю готовий:

- Зв'язано REST API бекенду та SSE потік з типізованим Web API Клієнтом (`api_client.ts`);
- Реалізовано OpenStreetMap GIS модуль (`osm_map_viewer.ts`) для відображення меж громади, критичної інфраструктури та загроз НС;
- 610/610 автоматизованих тестів пройдено з 100% успіхом.
